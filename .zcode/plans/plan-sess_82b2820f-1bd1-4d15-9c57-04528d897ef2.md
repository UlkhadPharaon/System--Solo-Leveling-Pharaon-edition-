# Moteur de domaines adaptatif + onboarding réel + Supabase local-first

## A. Fondations

### A1. Nouvelle entité `Domain` — `src/types.ts`
```ts
type DomainCategory = 'physical'|'creative'|'intellectual'|'craft'|'habit'|'financial'|'social';
type TrackingType = 'workout_log'|'project_phases'|'study_subjects'|'focus_sessions'|'budget_bucket'|'habit_checklist';
interface Domain {
  id: string; user_id: string | null;            // null = local-only, uid Supabase si sync
  label: string; category: DomainCategory; tracking_type: TrackingType;
  icon_ref: string; color_accent: string;        // résolus depuis category via table de styles
  goal_text: string;                             // texte libre, jamais réécrit
  target_metric?: { type: string; value: number };
  weekly_time_budget?: number;                   // heures
  created_at: number;
}
```
Extension de `PlayerProfile` : `onboarding_answers` (bloc 1 + réponses par domaine), `coaching_intensity`, `penalty_categories_allowed: ('in_app_restriction'|'creative_makeup'|'none')[]`, `constraint_text?` (jamais interprété médicalement). `domain_weights: Record<domainId, number>` calculé depuis les `weekly_time_budget` (normalisé somme=1) — champ `legacyCategory?: Category` sur Domain pour la non-régression.

### A2. Store domaines — nouveau `src/lib/domains.ts`
- Clé `aura_domains` (localStorage primaire), helpers CRUD, `computeDomainWeights()`, `getDomainStyle(domain)` (icône/couleur par `category`).
- `src/lib/utils.ts#getCategoryStyle` : délègue d'abord aux Domaines actifs, fallback sur la map legacy actuelle (données historiques intactes).

### A3. Remplacement Firebase → Supabase local-first
- Supprimer `src/lib/syncEngine.ts` (Firebase) et `firebaseConfig.ts` ; nouveau `src/lib/supabaseSync.ts` : auth anonyme Supabase, push debounce 5s de toutes les clés `aura_*` vers table `user_state(uid, key, value jsonb, updated_at)`, pull last-write-wins, kill-switch `aura_cloud_sync_enabled` conservé.
- `npm i @supabase/supabase-js`, `npm rm firebase`.
- `scripts/supabase-migration.sql` : tables `user_state` + table `domains` (colonnes du §spec, RLS basic sur uid) — à exécuter toi-même.
- `.env.local` placeholders : `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
- Si clés absentes → sync désactivée silencieusement, app 100% fonctionnelle en local (local-first).

## C. Pipeline de génération de quêtes

### C1. Nouvel endpoint `POST /api/generate-quests` — `server.ts`
- Abstraction provider : `LLM_PROVIDER=nvidia_nim|openrouter` (dev = NVIDIA NIM, prod = OpenRouter, plus tard Gemma E2B local — l'interface restera la même). `.env` : `NVIDIA_NIM_API_KEY`, `NVIDIA_NIM_BASE_URL`, `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`.
- Output **JSON structuré** (schéma de réponse imposé : liste de quêtes {domain_id, title, description, xp, difficulty}), garde-fous : aucun conseil médical, **template obligatoire pour tout domaine category=physical** (séries/reps/RPE fournis par l'app, pas inventés librement), pas de pénalités hors `penalty_categories_allowed`.
- Validation serveur de la réponse avant renvoi (schéma + bornes XP).

### C2. Client
- Après validation de l'onboarding : appel `/api/generate-quests` avec {vision, domains[], goal_text, coaching_intensity} ; les quêtes générées alimentent les premières missions de chaque domaine.
- Fallback déterministe : templates par tracking_type si l'API échoue (l'app n'est jamais bloquée sans réseau/clé).
- `domain_weights` calculé automatiquement (normalisation des budgets horaires), jamais inventé par le LLM.

## D. Migration de ton instance + non-régression

- `scripts/seed-domains.ts` (et exécution automatique au boot si `aura_domains` absent ET onboarding legacy complété) : crée les 4 Domaines depuis `defaultData.ts`. **Choix tranchés : Musculation→workout_log/physical, Cinéma→project_phases/creative, Bangre Neo Lab→project_phases/craft, École→study_subjects/intellectual.**

- `defaultData.ts` : les seeds en dur restent comme fallback preset mais ne s'appliquent plus aux nouveaux utilisateurs onboarding v2.
